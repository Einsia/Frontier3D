# L3 UE scoring reference

[Scoring guide](../scoring.md) · [Documentation](../../README.md)

L3 uses the same `python -m benchmark` entry point as L1/L2. Generation, independent collection, scoring and export are connected through the public CLI; setup is in the [installation guide](../../installation.md#configure-l3-ue). The implementation is under [harness/L3/release](../../../harness/L3/release/README.md).

## Tasks and score

The [task index](../../../harness/L3/release/task-index.json) defines 15 environments: six embodied, six game and three real-world tasks. Public packages are split into five Text2Environment and ten Image2Environment tasks. Native keys `l3-e/g/r` are retained, with Minecraft Village at `l3-g01`.

The final protocol is `l3-perceptual-quality-v5`, implemented by [quality_v5.py](../../../harness/L3/release/codebase/harness/L3/Suite/quality_v5.py):

~~~text
S_L3 = 0.60 visual_quality + 0.20 task_fidelity + 0.05 layout + 0.15 interaction
score_100 = 100 * S_L3
Harbor reward = score_100 / 100
~~~

All axes are in `[0,1]`. Any missing positive-weight axis leaves the result incomplete; weights are not redistributed. Supporting collection and correction stages supply layout and interaction measurements; their intermediate totals are not the final v5 score.

## Visual quality and task fidelity

The blinded judge is `gpt-6-astra/medium`. Its eight fixed criteria each contribute 10% of the task:

| Axis | Criteria |
| --- | --- |
| Visual quality, 60% | Shape/construction, materials, lighting, composition, functional detail, style |
| Task fidelity, 20% | Scene coverage, functional identity |

Each axis averages its criteria. Every task binds a fixed `reference_features` population in its scoring spec; generated objects do not redefine the denominator.

Each judgment records coverage, deviation, quality, quality band, required features, largest discrepancy, achieved features, discrepancies and evidence. **Quality is an evidence-based continuous judgment. The program does not multiply coverage and deviation into `c*(1-e)` or a squared variant.**

| Band | Prompt range | Validator maximum |
| --- | --- | ---: |
| absent | 0 | 0 |
| rudimentary | 0.01–0.34 | 0.34 |
| prototype | 0.35–0.64 | 0.64 |
| developed | 0.65–0.84 | 0.84 |
| exceptional | 0.85–1 | 1 |

The validator checks finite values, upper bounds, zero quality when coverage is zero, observations and candidate-evidence references. Not every prompt lower bound is enforced in code. `evidence_invalid` requires genuine missing, damaged or unusable evidence and null numeric values. Valid captures of empty, overexposed, occluded or rough content can still support low quality scores.

Independent views are bound to scene and manifest hashes. A contact sheet uses a fixed view order and includes the first overview at original resolution. Views are not selected by score. Required interior and close-up regions matter alongside overview quality; allowed voxel/low-poly styles are judged against task requirements.

## Layout, 5%

~~~text
layout = 0.25 support + 0.25 penetration + 0.30 navigation + 0.20 semantic
~~~

These contribute 1.25%, 1.25%, 1.50% and 1.00% of the task.

- **Support:** [physical_v2.py](../../../harness/L3/release/codebase/harness/L3/Suite/physical_v2.py), method `l3-physical-assets-v2.2`, checks visible geometry connections to assets and floor geometry. Scene and required-role axes are equally weighted; assets/entities use surface-area weighting and role-level macro averages. This is not a load-bearing stability certification.
- **Penetration:** affected overlap volume is accumulated per visible asset and capped at one, then aggregated by asset/role. Static rigid assemblies may contain internal combinations; interactive parts require actual pose-invariance evidence. Open render meshes use surface-crossing checks rather than invented closed volume. Unresolved geometry remains diagnostic.
- **Navigation:** independent pawn walking and doorway passage checks. Suite uses a default endpoint tolerance of 60 cm. A completed episode without an executable route can score zero.
- **Semantic:** the independent `layout_semantics` rubric checks adjacency, access and workspace organization.

[aggregate_v2.py](../../../harness/L3/release/codebase/harness/L3/Suite/aggregate_v2.py) combines corrected physical/motion evidence before v5 aggregation. Follow raw reports and method versions for each value.

## Interaction, 15%

~~~text
interaction = 0.40 local + 0.25 motion + 0.35 state_and_workflow
local_entity = 0.20 presence + 0.50 positive_physical_effect + 0.30 invalid_reach_rejected
state_and_workflow = 0.50 resource_state + 0.50 continuous_workflow
~~~

Local, motion and workflow contribute 6%, 3.75% and 5.25% of the task. Local objects are averaged by role, then macro-averaged across roles so duplicate objects cannot dilute a required mechanism failure. Positive actions require observable geometry, pose, light, occupancy or trusted-inventory changes. Invalid reach and missing prerequisites must be rejected. A candidate's success string alone is insufficient.

Motion checks use actual sampled trajectories for moving mechanisms and related objects. Penetration scores zero; unresolved measurement remains null. Switches, fixed ladders, keys and some inventory actions may have no rigid-body trajectory under the explicit applicability rules. Doors and lifts require actual movement. Discrete samples do not establish continuous-time collision freedom.

Resource state measures fixed end predicates. Continuous workflow requires all specified goals, routes and operations. [observations.py](../../../harness/L3/release/codebase/harness/L3/Suite/observations.py) defines task predicates, such as cargo placement, lift height, tool return and unrelated circuit preservation.

[MinecraftVillage](../../../harness/L3/release/codebase/harness/L3/MinecraftVillage) has dedicated entity groups, resource chains and workflow collectors, connected through `l3_matrix_mc.py` to the same final layout/interaction axes and v5 aggregation. Use its dedicated predicates.

## Independent collection and completion

[verify.py](../../../harness/L3/release/verify.py) checks a frozen submission and runs independent collection and judging:

1. Require a fresh output and an absent reward file.
2. Verify `submission-manifest.json`, task/model/effort and source bindings.
3. Require the independent UE engine, GPU/Docker environment and host-side judge provider.
4. Copy the frozen v5 specs into the evaluation batch and collect with `evaluate_l3_submission.py --collect-only`.
5. Run `score_one.py` and `l3_matrix_scoring.worker` for geometry, interaction, visual judgment and aggregation.
6. Require v5, `status=measured`, `missing_axes=[]`, a finite score in `[0,100]`, and unchanged submission identity.
7. Write the normalized reward and `verifier-result.json` with the report hash.

Missing infrastructure, API failures and incomplete axes retain evidence and fail completion rather than inventing a zero reward. Judge caches bind the prompt, schema and images. Nonretryable HTTP failures and insufficient balance stop the request; other failures may back off, so outer runtime budgets still matter. Visual quality/fidelity does not demonstrate interaction success; inspect actual trajectories, actions and end predicates.
