# Integration and submission

The files `BenchEntity.h`, `BenchObserver.h`, `BenchInventory.h` and `INTERFACE.md` describe the provided `BenchRuntime` plugin. Enable this plugin and add `BenchRuntime` to your gameplay module dependencies. **Do not implement or modify the observer.** Derive a component from `UBenchEntity` and override `Interact_Implementation(APawn*, const FString&, const FString&)` for gameplay. Give each required interactive actor its exact EntityId. Register the 11 buildings as `building.house01` … `building.house08`, `building.smithy01`, `building.smithy02`, `building.storehouse`, role `building`. Other useful roles are door, gate, chest, crop, editable_block, furnace, prop, path, terrain, tree and water. Tags and semantic state assist inspection but do not replace real geometry. Use distinct actors for moving doors/lids and give their primitive components meaningful stable names. `SemanticState` may include open, harvested, planted, contents, inventory values as strings; observers verify geometry separately.

Attach exactly one provided `UBenchInventory` component to the player pawn and begin with an empty inventory. Use its `Count`, `Grant` and `Consume` methods, with the item names `seeds`, `crops`, `processed`, `tools`. A bundle counts as one item. All inventory changes must use this component; do not keep a second independent inventory. The verifier reads these counters directly and replaces the provided plugin with its trusted implementation. Gameplay must enforce all action preconditions.

Supply `project/bindings.json` with:
- `version: 1`;
- `entities`: mapping each required interaction ID to `approach_cm: [x,y,z]` (standing capsule centre on stable ground), `look_cm: [x,y,z]` on its visible interactive surface. Door/gate entries additionally have `crossing_from_cm`, `crossing_to_cm` at capsule-centre height on opposite sides of the CLOSED aperture, 150–300 cm apart; these must cross the actual entrance. A closed probe must hit the named door/gate, not a different wall. Directions must work for the open leaf too;
- `views`: mapping `overview`, `street`, `interior`, `farm`, `smithy`, `waterfront` (legacy name for an outskirts view; it does not require water) to `position_cm` and `look_cm`. These are camera hints, not alternative scenes. `overview` is your predicted reference camera: match the supplied screenshot framing, optionally include `horizontal_fov_deg` (20–120; default 90), and omit HUD. The evaluator renders this frozen camera at the reference resolution, with no image warping or best-view selection; camera prediction error is part of the image error;
- `journey`: an ordered list of 4–12 `{direction:[x,y,0],seconds:float}` walking segments (each 0.2–15 seconds) beginning at default player spawn and covering at least 25 metres on connected paths, visiting at least two districts without teleporting. Record intended landmarks in README. The benchmark separately composes a house→farm→smithy state-persistence task.

No trusted test files are visible. Hidden variants may reverse action order, repeat actions, approach from a different angle and measure the geometry between endpoints. Do not invent test output, scores or screenshots. Report limitations honestly.


## Submission

Produce exactly one top-level `.uproject` with EngineAssociation `5.8`, `Config/`, `Source/`, game and Editor Target.cs files, `README.md`, and `bindings.json`. Use `BuildSettingsVersion.V7` and `EngineIncludeOrderVersion.Latest`. Procedural construction and authored `Content/` assets/maps are both allowed. Use `/Engine/Maps/Entry` as the startup map with your default game mode if you do not ship a real map. All geometry, materials, lighting and UI must appear at runtime. Include the plugin descriptor in the project; the environment provides its trusted files. README must explain controls, district layout, interaction preconditions and known limitations.

This is one image-and-text agent trial inside a fixed time budget. You may repeatedly edit, compile, run the project, render and inspect screenshots, test your own interactions, and fix your implementation. Build errors and your own visual observations are valid feedback. No human corrective feedback or hidden evaluation scores are provided during the trial. Use the installed engine and public workspace tooling; do not access the internet to acquire assets. Local build products (`Binaries/`, `Intermediate/`, `Saved/`) and genuine preview images are allowed during development. The verifier rebuilds the final source/assets independently and does not trust generated build products or agent-reported successes.

You may use the organizer-provided offline material pack listed in `input/ASSETS.md` and the engine content explicitly available in the environment. You may select, combine and modify these textures/materials and create your own additional materials. Include required texture/material assets in `project/Content/` or a documented project-local generation path, and record used asset IDs and licenses in `project/assets_used.json`. Do not copy a prebuilt reference world, furnished building prefab or ready-made gameplay system. The material library supplies surfaces, not the village layout or interactive implementation. No Marketplace login or runtime download is required.

A benchmark trial requires a functioning engine, compiler and preview facility before its timer starts. A source-only diagnostic attempt with an unavailable engine must be explicitly labeled as such and is not comparable to an equipped agent trial. Render/build failures and infrastructure failures are reported separately from scene quality; an unexecuted scene receives no scene-quality score.
